# Endterm: проверка и сценарий защиты

Критерии из предоставленной таблицы: сохранение и чтение с сохранностью после перезапуска; две разные проверки ввода; smart function с входом и результатом; два расчёта и график с обновлением; защита и заблокированный случай. Это сценарий живой демонстрации, а не замена её скриншотами.

## Аудит

| -------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Data storage   | `POST /reports`, `GET /reports/my`, PostgreSQL Supabase, private Storage для фото                                           | Изменений архитектуры не требуется                                                                            |
| Validation     | Общая Zod-схема на API, trim/min, дата не в будущем, диапазоны GPS/reward; ошибки показаны в форме                          | Явные сообщения `Item name is required` и `Color is required` для пустого/пробельного ввода                   |
| Smart function | `matching.ts`: сравнение названия/описания/цвета, нормализация и опечатки; публикация и recheck запускают подбор до Gemini  | Gemini не требуется; демонстрируем алгоритмический подбор, не называем его работающим генеративным ИИ         |

## Подготовка

1. На новой базе выполнить миграции `001`–`007` по порядку и при необходимости `database/seed.sql`. На существующей базе применить только ещё не применённые миграции; не повторять `001` и не сбрасывать данные. В частности нужна `007_personal_analytics.sql`. Проверить наличие private bucket `item-images` и таблицы `report_images` в том же Supabase-проекте, который указан в backend/.env.
2. Заполнить backend/.env и mobile/.env по примерам. Серверный service-role key хранить только на сервере. Оставить `GEMINI_API_KEY=` пустым и перезапустить API: это проверяет независимость smart function от Gemini. Сеть до API/Supabase всё равно нужна.
3. `npm ci`, `npm run build`, `npm run typecheck`, `npm test`. Запустить API (`npm run dev:api`) и Expo (`npm run dev:mobile`) либо обновить сервер и собрать новый APK по DEPLOYMENT.md. Старый APK не содержит новый экран.
4. Подготовить два обычных подтверждённых аккаунта A и B, без staff/admin-ролей. Подготовить фото рюкзака. У телефона должен быть доступ к адресу API из mobile/.env. Для повторяемого результата используйте один и тот же текст в паре объявлений.

## Живая демонстрация (около 8 минут)

1. **Исходные числа.** Войти как A → Profile. Нажать Refresh analytics; записать Total reports = N и Bags = B (если категории нет, B=0). Для чистого аккаунта N=0, return rate=0%, пустой график — ожидаемое состояние.
2. **Required field.** Reports → создать LOST, категория Bags; заполнить место, цвет Black, дату на час раньше текущей. В имени ввести только пробелы и нажать Submit report. Ожидается ошибка с `item_name` и `Item name is required`; форма остаётся открытой, запись не сохраняется. Можно повторить с пустым цветом: ошибка `color` / `Color is required`. Это одна группа правил, а не две разные проверки.
3. **Вторая проверка.** Исправить имя на `Black Nike backpack`. Ввести корректно оформленную дату на следующий день и отправить. Ожидается `Date cannot be in the future`, запись не сохраняется. Затем исправить дату на час раньше текущей. Описание `Black backpack with a blue keychain`, цвет Black. Отправка теперь успешна. Название/описание/цвет запомнить для B.
4. **Хранение и обновление анализа.** В Reports увидеть новое LOST. Полностью закрыть и открыть приложение, снова открыть Reports: запись осталась. Это отдельные операции сохранения и чтения из PostgreSQL. В Profile → Refresh analytics получить N+1, Bags=B+1. Диаграмма показывает абсолютные значения и подписи, длины столбцов масштабируются относительно максимальной категории.
5. **Smart function без Gemini.** Под аккаунтом B создать FOUND с теми же названием, описанием, цветом и местом, датой на час раньше текущей. Добавить фото, вопрос `What is inside the front pocket?`, ответ `Red notebook and USB drive`. Отправить. Вернуться в A → Matches (при необходимости открыть своё LOST → Recheck matches). Ожидается предложение 100% с разбивкой name 50 / description 30 / color 20. Допуск строго >75%; одинаковый цвет без похожих имени/описания недостаточен. Одного аккаунта для пары недостаточно: собственные объявления исключены. Ошибка/отсутствие Gemini не блокирует этот результат. Предложение ещё не доказывает владение.
6. **Защита.** До подтверждения владения чат закрыт. A подтверждает предложение, вводит неправильный ответ на вопрос: доступ к чату остаётся закрытым; API возвращает 403. Для успешного продолжения ввести правильный ответ до исчерпания лимита попыток. Не тратить все попытки на единственной демонстрационной паре. Дополнительно показать запрос `GET /analytics` без Authorization: 401, никаких данных. Обычный B при `GET /reports/<ID LOST аккаунта A>` со своим токеном получает 403. Токены на экран защиты не выводить.
7. **Два расчёта и график.** В Profile показаны COUNT всех своих объявлений, COUNT возвращённых и return rate = returned / all saved ×100 (при нуле объявлений 0%). Все статусы, включая DRAFT/CLOSED, входят в знаменатель; это доля объявлений, а не уникальных предметов. Категории строятся по тому же набору. При желании завершить подтверждение/возврат через существующий workflow и обновить: returned и процент изменятся. Для обязательного обновления данных достаточно шага 4.

Преподаватель может изменить название, категорию или дату: повторить отправку/обновление и показать реальный результат. Не фиксировать ожидаемое число объявлений на заранее заполненном аккаунте — сравнивать с исходным N.

## Проверки и границы

- `npm test`: matching, обязательные поля/дата, авторизация и область аналитики; `npm run build` и `npm run typecheck`: сервер/shared и мобильные типы.
- `npm run test:acceptance` с `ALLOW_TEST_USERS=true` — только на отдельном тестовом Supabase с применёнными миграциями и запущенным API. Скрипт создаёт и удаляет тестовые данные; проверяет пустую аналитику, изменение после сохранения, изоляцию аккаунтов, подбор и защищённый workflow. Подключение описано в TESTING.md.
- Проверки типов и unit-тесты не подтверждают применение SQL на вашем Supabase, доступность SMTP, работу устройства или Gemini. Пройти сценарий на целевой базе и телефоне до защиты. Gemini image analysis остаётся необязательной внешней интеграцией, её успешная работа не заявляется.
